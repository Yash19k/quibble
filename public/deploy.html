Deploy guide · your own copy, your own AWS account

Put your own Quibble on AWS

Quibble is open source, and the same repository that runs this site deploys a complete copy to any AWS account with a handful of commands. This guide walks through them one at a time and explains what each one does, so by the end you know what CloudFormation, Lambda, API Gateway, DynamoDB and S3 are actually doing for you.

Plan on roughly an hour the first time, plus up to a day of waiting if you ask AWS to raise your Lambda quota (step 6). You need a computer running Windows, macOS or Linux, an AWS account and an email address. New to how Quibble is built? Take the interactive tour first.

Part A

The big picture

Everything Quibble needs is described in one file, aws/template.yaml. When you deploy, AWS CloudFormation reads that file and creates every piece as a single unit called a stack (named quibble unless you choose otherwise). One command creates it, later deploys update it, and one command deletes all of it.

Read it from the left. At deploy time your computer packages the backend code, SAM uploads the zip to an artifact bucket, and CloudFormation builds the stack. Then a script copies the website files from public/ into the stack's S3 bucket. At play time a browser loads those files from S3, calls the HTTP API for things like logging in and leaderboards, and holds a WebSocket open for the game itself. Lambda functions do the work and keep every bit of state in DynamoDB, because a function forgets everything when it finishes.

Along the bottom is the safety net: EventBridge runs the monitor function every minute to load the site, call the API and open a WebSocket. CloudWatch alarms call the same function when errors or throttling show up, and it emails you through SNS.

Part B

The AWS pieces, and what each does here

You don't need to know these services before you start, but the steps make more sense once you know what you're creating. Each card says what the service is in general and exactly how Quibble's template uses it.

CloudFormation and SAM

What it is. Infrastructure as code. You describe resources in a template and CloudFormation creates, updates or deletes them together, in the right order, rolling back if something fails. SAM (Serverless Application Model) is shorthand on top: one AWS::Serverless::Function line becomes a Lambda function, its IAM role and its triggers.

In Quibble. aws/template.yaml starts with Transform: AWS::Serverless-2016-10-31, which tells CloudFormation to expand the SAM shorthand. The SAM CLI's sam build and sam deploy package the code and hand the template over. The stack's outputs (the site link, the API addresses, the table names) are how the other scripts find what was created.

AWS Lambda

What it is. Functions that run when something calls them, then stop. You pay per request and per millisecond of run time, and nothing while idle. Each run starts with no memory of the last one.

In Quibble. Six Node.js 22 functions on arm64: api, ws-connect, ws-message, ws-disconnect, game-timer and monitor. Lambda has no setTimeout that outlives a request, so game-timer is invoked asynchronously with each deadline and schedules the next one. All of them share the account's concurrency quota: how many copies may run at the same moment in a region (step 6).

API Gateway: HTTP API and WebSocket API

What it is. The front door that turns internet traffic into Lambda calls, with throttling built in. Quibble uses both kinds it offers:

HTTP APIWebSocket API
ConnectionOne request, one response, then it's overStays open for the whole game
Who can speakOnly the browser starts a conversationThe server can push to the browser at any time
Routes/api/{proxy+}: every path goes to api, which has its own route table$connect, $default, $disconnect, each with its own function
Used forSign-up, login, leaderboards, history, the admin consoleJoining, the countdown, answers, results, reactions
Billed perRequestMessage, plus connection minutes

The trick worth knowing. Lambda can't hold a socket open, so API Gateway holds it. A function that wants to tell 250 players "next question" calls the API Gateway Management API (PostToConnection) once per socket. The template caps both APIs at 1,000 requests a second with bursts of 2,000.

Amazon DynamoDB

What it is. A key-value database with no server to size. Every item lives under a partition key, and each key handles about 1,000 writes a second. On-demand billing charges per read and write.

In Quibble. Nine tables, all PAY_PER_REQUEST. Time to live (TTL) deletes old games, sockets and rate-limit counters for free. Users and Questions have point-in-time recovery switched on, so you can restore them to any second in the last 35 days.

Amazon S3 static hosting

What it is. Object storage. A bucket can serve files straight to browsers if its bucket policy allows public reads.

In Quibble. FrontendBucket holds the HTML, CSS and JavaScript, and FrontendBucketPolicy lets anyone read (never write) them. Players use the HTTPS address https://<bucket>.s3.<region>.amazonaws.com/index.html. That address has no index page, so links always name a file. S3 can't send security headers, which is why each page carries its Content-Security-Policy in a <meta> tag.

AWS IAM

What it is. Who may do what. Users are people (you, at the command line). Roles are worn by services, so a Lambda function gets temporary permissions without any stored password.

In Quibble. Each function's Policies list becomes its own role. ws-connect, for example, can only read the Users table and read or write the Connections table. Because the template creates roles, the deploy passes --capabilities CAPABILITY_IAM, your explicit "yes, I know this stack creates IAM roles".

CloudWatch, EventBridge and SNS

What they are. CloudWatch collects logs and metrics and raises alarms. EventBridge runs things on a schedule or when an AWS event happens. SNS (Simple Notification Service) delivers a message to every subscriber of a topic, here by email.

In Quibble. Log groups kept for 14 days (the LogRetentionDays parameter), 14 alarms, a dashboard and custom metrics in the Quibble namespace. EventBridge runs monitor every minute and whenever a deploy of this stack fails; monitor writes the email and publishes it to AlertsTopic.

Part C

What it costs

Almost everything is pay-per-use, so a stack nobody is playing on costs very little. The prices below are approximate: they vary by region and change over time, so check the AWS pricing pages or the AWS Pricing Calculator for your region.

Sitting idle
Roughly under a dollar a month (approximate). One thing always runs: the uptime monitor, about 43,000 small Lambda runs a month, which fit in Lambda's free allowance, plus as many HTTP API calls, WebSocket handshakes and S3 page loads, which come to a few cents. CloudWatch charges about $0.10 a month for each alarm beyond the first 10, and the stack has 14.
A game
A 10-question game with 5 players costs a fraction of a cent (approximate). Lambda, API Gateway and on-demand DynamoDB charge per request, and a game is a few thousand small requests.
Free allowances
Lambda, DynamoDB and SNS email (1,000 a month) have monthly free allowances, and newer accounts may also get free-tier credits. What applies depends on when your account was created; the Billing console shows it.
What can surprise you
A forgotten test stack, a script that logs errors in a loop (CloudWatch charges for log data stored and ingested), or a big event. Step 1's budget alarm is there so a surprise reaches your inbox in days, not on the monthly bill.

Before the steps

Commands that differ between terminals come in two versions. Pick yours and the guide shows only that one. On Windows, PowerShell and Git Bash both work. On macOS or Linux, pick bash (zsh is the same here).

Step 1 of 11

Protect your account first

Before you create anything, make the account safe to experiment in. All of this is in the AWS console in your browser.

  1. Lock away the root user. The email address you signed up with is the root user, which can do anything, including close the account. Sign in as root once, open Security credentials and turn on multi-factor authentication (MFA). Never create access keys for root.
  2. Set a budget alarm. In Billing and Cost Management, open Budgets, choose Create budget and use a template: Zero spend budget emails you as soon as anything costs money, or Monthly cost budget with a small amount such as $5.
  3. Create an IAM user for yourself. In IAM, choose Users, then Create user, give it console access and attach the AdministratorAccess policy. Sign in as that user from now on and turn on MFA for it too.
  4. Create an access key for the command line. On your new user's Security credentials tab, choose Create access key with the Command Line Interface (CLI) use case. Keep the window open: step 4 needs both values, and the secret is shown only once.

Treat the access key like a password

Anyone with it can run up a bill in your name. Never paste it into code, a commit, a chat or a screenshot. Quibble's .gitignore already keeps .env and aws/.jwt-secret out of git; keep it that way. If a key leaks, deactivate it in IAM straight away.

What you're learning

Root user vs IAM identities, and MFA. AWS has no spending cap: a budget warns you, it doesn't stop anything. AdministratorAccess is broad, but deploying this stack means creating IAM roles, so the deployer needs wide rights; in a team you'd use a separate sandbox account or a tighter policy. AWS IAM Identity Center (single sign-on) is the more modern way to sign in, and the scripts support it too (step 4).

Step 2 of 11

Pick a region

A region is a group of AWS data centres in one part of the world, named like us-east-1, eu-west-1 or ap-south-1. The whole Quibble stack lives in one region, so pick the one closest to your players: every answer travels to it and back.

Write the region code down. You'll make it your default in step 4, and the deploy, the quota check and the seed script all use that default.

The console has a region picker too

It sits at the top right of every console page. If you ever "lose" your stack, functions or tables, you're almost always looking at the wrong region.

What you're learning

Regions are separate. Most resources (functions, tables, APIs) and most quotas are per region, and prices differ a little between regions. IAM and billing are global: one user and one budget cover every region.

Step 3 of 11

Install the tools

Four programs, all free:

  • Git, to download the code. On Windows, Git for Windows from git-scm.com also installs Git Bash.
  • Node.js 22 or newer from nodejs.org (the LTS version is fine). The deploy scripts and the backend are JavaScript; package.json asks for Node 22+.
  • AWS CLI version 2, the general command line for AWS. On Windows, run the installer below or download it from the AWS CLI install guide, which also covers macOS and Linux.
  • AWS SAM CLI 1.123 or newer, which builds and deploys the template. On Windows, download the 64-bit installer from the SAM CLI install guide. Older versions can't deploy the game timer's RecursiveLoop setting.
PowerShell · Windows only
# installs the AWS CLI v2 from Amazon's official installer
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi

Then open a new terminal, so it picks up the updated PATH, and check that all four answer:

PowerShell or bash
git --version
node --version     # v22 or newer
aws --version      # aws-cli/2...
sam --version      # 1.123.0 or newer

No Docker needed for this

Docker is only for running Quibble on your laptop with DynamoDB Local (the "Play locally" card on How it works). Deploying doesn't use it.

What you're learning

Two command lines with different jobs. aws can call any AWS API, one request at a time. sam works at the level of a whole application: it builds the function code and drives CloudFormation. Quibble's own scripts use a third route, the AWS SDK for JavaScript, which reads the same credentials as both.

Step 4 of 11

Connect the CLI to your account

Give the CLI the access key from step 1 and the region from step 2. It asks four questions; answer json to the last one.

PowerShell or bash
aws configure
aws sts get-caller-identity

The second command asks AWS "who am I?". The answer should name your IAM user, not root:

Example output
{
    "UserId": "AIDAEXAMPLEUSERID",
    "Account": "111122223333",
    "Arn": "arn:aws:iam::111122223333:user/your-user-name"
}

Using IAM Identity Center instead of an access key? Run aws configure sso once, aws sso login whenever the session expires, and point every terminal at the profile you created:

PowerShell
$env:AWS_PROFILE = "your-profile-name"
bash
export AWS_PROFILE=your-profile-name

What you're learning

Where credentials live. aws configure writes two small files in the .aws folder of your home directory: credentials (the key) and config (the region). The CLI, the SAM CLI and the AWS SDK used by Quibble's scripts all read them, unless environment variables such as AWS_PROFILE or AWS_REGION in the current terminal say otherwise. That lookup order is called the credential provider chain.

Step 5 of 11

Get the code and choose the admin login

Download the repository and install its packages. If you plan to change the game, fork it on GitHub first and clone your fork instead.

PowerShell or bash
git clone https://github.com/Yash19k/quibble.git
cd quibble
npm install

npm install installs the deploy tools at the top level, then its postinstall step installs the Lambda functions' own packages in aws/backend. Next, copy the example settings file:

PowerShell
Copy-Item .env.example .env
bash
cp .env.example .env

Open .env in any editor and set the admin account that step 9 will create. Use your own email and a password of at least 10 characters:

In the .env file
ADMIN_EMAIL=you@example.com
ADMIN_USERNAME=admin
ADMIN_PASSWORD=a-long-password-only-you-know

# Optional: a different CloudFormation stack name (default: quibble)
# QUIBBLE_STACK=quibble

What you're learning

Configuration stays out of the code. .env holds settings that differ per person and must never be shared, so git ignores it; .env.example is the safe, committed template. The other lines in it only affect the local dev server (on AWS the same settings are template parameters, see Ship updates).

Step 6 of 11

Ask AWS to raise the Lambda quota

New AWS accounts may run only 10 Lambda functions at the same moment per region, shared by every function. That's plenty for trying Quibble with a few friends, but in a full room 250 players answer within the same fraction of a second and queue behind those 10 slots. The AWS standard is 1,000, raising it is free, and it's usually approved within a day, so ask now and keep going while you wait.

PowerShell or bash
npm run quota:lambda                # the current value and any open request
npm run quota:lambda -- --request   # ask for 1,000 (Service Quotas code L-B99A9384)
Example output
Lambda concurrent executions in eu-west-1: 10 (AWS standard: 1000)

Request the standard 1000 with:  npm run quota:lambda -- --request

AWS emails the account owner when it decides; run npm run quota:lambda again to check. Until then the game still works, just with slower phase changes in big rooms. To soften that, deploy with a longer grace period for late answers (npm run deploy -- LateGraceMs=5000 in step 8) and set it back to the default 1500 after the raise.

What you're learning

Service quotas and concurrency. Every AWS service has limits per account and region; some can be raised on request through Service Quotas. Lambda concurrency is how many copies of your functions run at once. When it's full, new calls are throttled (refused), and Quibble's page resends them with backoff, so nothing is lost but things slow down. The template deliberately reserves no concurrency for any function: a reservation carves slots out of the shared pool, and isn't possible at all on a 10-slot account.

Step 7 of 11

Run the preflight check

The preflight script checks everything the earlier steps set up, without changing anything: the SAM CLI version, that your credentials work and a region is set, the Lambda quota (it wants 500 or more), and, once a stack exists, whether any games are live on it.

PowerShell or bash
npm run preflight
Example output, quota not raised yet
Quibble preflight
  [ok]   AWS SAM CLI 1.140.0
  [ok]   AWS credentials: account 111122223333 (arn:aws:iam::111122223333:user/your-user-name)
  [ok]   Region: eu-west-1
  [FAIL] Lambda concurrency quota is 10. A 250-player game needs 500 or more (the AWS standard is 1000).
         Ask AWS for the standard 1000 (free; usually approved within a day):
           npm run quota:lambda -- --request
         ...
  [ok]   Stack "quibble" is not deployed yet (nothing live to disturb).

Preflight failed: 1 problem(s) above.

Fix every [FAIL] it reports; each one prints a hint underneath. The quota is the one exception you may accept for now: npm run preflight -- --allow-degraded turns that failure into a warning. You don't strictly have to pass preflight to deploy, because npm run deploy runs it again first in a warn-only mode that never stops the deploy.

What you're learning

Check before you change. Every check is a read-only API call: STS GetCallerIdentity for "who am I", Lambda GetAccountSettings for the quota, a DynamoDB scan of the Games table for live games. Finding problems this way is cheaper than finding them halfway through a deploy, and it's the habit to keep before every event.

Step 8 of 11

Deploy

One command does all of it. The first deploy takes a few minutes while CloudFormation creates several dozen resources.

PowerShell or bash
npm run deploy

To deploy to a region other than your default, set it for this terminal first:

PowerShell
$env:AWS_REGION = "eu-west-1"
npm run deploy
bash
AWS_REGION=eu-west-1 npm run deploy

What npm run deploy does, in order

  1. Preflight, warn-only. The same report as step 7. It never stops the deploy.
  2. The login secret. Login tokens are signed with a secret. The first deploy generates a random one and saves it in aws/.jwt-secret (git-ignored); later deploys reuse it, so players stay logged in. It also names the flag images, so the file name doesn't give a flag question's answer away.
  3. sam build copies aws/backend into aws/.aws-sam/build and installs its production packages, ready to zip.
  4. sam deploy uploads the zips and the template, and CloudFormation works out a change set, the list of resources to create, change or delete, then applies it.
  5. Publish the website (aws/scripts/publish-frontend.mjs). It reads the stack's outputs, writes config.js with your two API addresses, narrows each page's Content-Security-Policy to exactly those two hosts, uploads public/ to the bucket, deletes files that no longer exist locally, and prints your link.
What deploy.mjs runs for you, in the aws folder
sam build
sam deploy --stack-name quibble --resolve-s3 --capabilities CAPABILITY_IAM \
  --no-fail-on-empty-changeset --parameter-overrides JwtSecret=**** [your Name=value pairs]
--stack-name quibble
The stack's name, from QUIBBLE_STACK if you set it.
--resolve-s3
Let SAM create (once per region) and use its own bucket for the uploaded code, in a stack called aws-sam-cli-managed-default.
--capabilities CAPABILITY_IAM
Your consent that the template creates IAM roles. CloudFormation refuses without it.
--no-fail-on-empty-changeset
A redeploy with nothing changed counts as success, not an error.
--parameter-overrides
Values for the template's Parameters: the secret, plus anything you add after npm run deploy --.

At the end it prints the link to share. Keep the terminal output; you'll need the API addresses in step 11.

Example output, the last lines
Frontend published. Share this link with players:
  https://<bucket>.s3.<region>.amazonaws.com/index.html

First deploy? Run "npm run seed" to create the admin account and sample questions.

Lost it? The stack's outputs are always there to read back. This lists WebsiteUrl, HttpApiUrl, WebSocketUrl, FrontendBucketName, DashboardUrl and the rest:

PowerShell or bash
aws cloudformation describe-stacks --stack-name quibble --query "Stacks[0].Outputs" --output table

Back up aws/.jwt-secret

If it's lost (a new laptop, a fresh clone), the next deploy makes a new one: everyone is logged out and the flag images get new names. Copy it somewhere private, next to your password manager, not into git.

What you're learning

Infrastructure as code and stack outputs. You never clicked "create table" nine times: the template is the source of truth, and CloudFormation makes the account match it. Watch it happen in the CloudFormation console under Stacks, then quibble, then Events. The API addresses don't exist until the deploy creates them, which is why the website gets a generated config.js instead of hard-coded URLs, and why the same code works for anyone's copy.

Step 9 of 11

Create the admin account and load questions

The tables start empty. The seed script creates the admin account from your .env and loads the sample question bank (12 categories). Only the first deploy needs it.

PowerShell or bash
npm run seed
Example output
Created admin: you@example.com
Added <n> new questions (0 already existed).

It may generate the password for you

Your site is public, so the script refuses weak passwords. If ADMIN_PASSWORD is missing, still the example value, or shorter than 10 characters, it generates a strong one and prints it once with "save it now". Save it: running seed again won't change an existing admin's password.

Running it again is safe: it makes sure the account still has the admin role and adds only questions that aren't there yet. Now open your WebsiteUrl, log in with the admin email and password, and choose Admin in the game header to reach admin.html: live games, players, the question bank, an announcement banner and system health.

What you're learning

Your credentials can reach the data directly. The seed doesn't go through the website or the API. It runs on your computer, finds the Users and Questions table names in the stack outputs, hashes the password with bcrypt locally and writes straight to DynamoDB with your IAM user's permissions. The Lambda functions do the same thing with their roles' narrower permissions.

Step 10 of 11 · optional

Turn on email alerts

The alarms and uptime probes already run; they just have nobody to tell. Give the stack an address with the AlertEmail parameter and, if you like, a time zone (an IANA name such as Europe/London; the default is UTC) for the times in the emails:

PowerShell or bash
npm run deploy -- AlertEmail=you@example.com AlertTimeZone=Europe/London

AWS then sends that address an email titled "AWS Notification - Subscription Confirmation". Click Confirm subscription in it (check spam), then send yourself a test:

PowerShell or bash
npm run alerts:test   # sends a test email and says whether the address has confirmed

From then on you get an email when the site, the API or the WebSockets stop answering (and when they're back), when errors are logged, when Lambda or DynamoDB throttle, when a deploy fails or rolls back, and on sensitive admin actions such as a ban, a password reset or a new admin.

What you're learning

Template parameters and conditions, plus pub/sub. The template only creates the email subscription when AlertEmail isn't empty (its HasAlertEmail condition). Parameters you pass stay set for later deploys until you change them. SNS asks for confirmation so nobody can sign a stranger up for email, and any number of addresses can subscribe to the same topic (the AlertsTopicArn output) in the SNS console.

Step 11 of 11

Check that it works

  1. Ask the API if it's healthy. /api/health reads DynamoDB, so an answer of ok: true proves API Gateway, Lambda and the database all work. Use the HttpApiUrl output.
PowerShell
Invoke-RestMethod "<HttpApiUrl>/api/health"
bash
curl "<HttpApiUrl>/api/health"
  1. Play a real game. Open your WebsiteUrl (it must end in a file name such as /index.html), host a game, and join it with the six-letter code from a private window or your phone.
  2. Look at it from the inside. Open the DashboardUrl output for the CloudWatch dashboard, and the admin console's System health page for response times and table sizes.
  3. Optional: run the end-to-end tests against it. These play full games over real WebSockets, using the HttpApiUrl and WebSocketUrl outputs and your admin login.
PowerShell
$env:QA_API = "<HttpApiUrl>"
$env:QA_WS = "<WebSocketUrl>"
$env:ADMIN_EMAIL = "<admin email>"
$env:ADMIN_PASSWORD = "<admin password>"
$env:QA_SKIP_FULL = "1"   # skip the test that signs up about 250 accounts
npm run test:e2e
bash
# QA_SKIP_FULL=1 skips the test that signs up about 250 accounts
QA_API="<HttpApiUrl>" QA_WS="<WebSocketUrl>" ADMIN_EMAIL="<admin email>" \
  ADMIN_PASSWORD="<admin password>" QA_SKIP_FULL=1 npm run test:e2e

The tests leave things behind

They sign up test players and add a "Load Test" question category through the admin API. That's fine on a fresh copy, but on a site people already use, run them against a separate test stack instead (see Ship updates).

What you're learning

Verify each layer, from the outside in. The health call checks the back end without the website; the game checks everything together; the dashboard shows what happened underneath. It's the same three-part probe the monitor function runs every minute: load the page, call /api/health, open a WebSocket.

Part D

Troubleshooting

The messages below are the ones Quibble's scripts and AWS actually print. Open the one you're seeing.

"AWS SAM CLI not found" or "sam is not recognized"

The SAM CLI isn't installed, or this terminal was open before you installed it. Install it (step 3), close every terminal, open a new one and run sam --version. The same goes for aws.

"AWS SAM CLI 1.x is too old; 1.123.0 or newer is needed"

The game timer uses Lambda's RecursiveLoop: Allow setting (each timer schedules the next one, and without it Lambda stops the chain after about 16 hops, mid-game). Older SAM versions don't know that property. Install the latest SAM CLI over the old one.

PowerShell: "npm.ps1 cannot be loaded because running scripts is disabled"

Windows blocks PowerShell scripts by default, and npm installs itself as one. Allow scripts you've installed locally for your user only, or use Git Bash instead:

PowerShell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
"No AWS region set" or "AWS credentials don't work"

Run aws configure again (step 4) and check aws sts get-caller-identity answers. With Identity Center, the session has expired: run aws sso login, and make sure AWS_PROFILE is set in this terminal. An AWS_REGION or AWS_PROFILE set earlier in the same terminal wins over your saved defaults.

"Could not read stack "quibble" ... Did you run "npm run deploy"? Is your AWS region set?"

The seed, publish and alerts scripts find your resources through the stack's outputs. This means they looked in a region or under a stack name where it doesn't exist. Use the same region you deployed to, and if you deployed with QUIBBLE_STACK, set it again in this terminal (or in .env).

The deploy fails on FrontendBucketPolicy, or the site shows an XML "AccessDenied" page

S3 Block Public Access is switched on for your whole account, and it overrides the bucket's own setting. In the S3 console, open Block Public Access settings for this account and turn off "Block public access to buckets and objects granted through new public bucket policies" (for the failed deploy) and "... through any public bucket policies" (for AccessDenied on a deployed site). Then deploy again. The template itself still blocks public ACLs; only the read-only bucket policy needs this.

Also check the address ends in a file name: https://<bucket>.s3.<region>.amazonaws.com/ on its own has no index page and answers with an XML error.

"Stack is in ROLLBACK_COMPLETE state and can not be updated"

The very first deploy failed, and CloudFormation rolled back by deleting what it had made. A stack in that state can only be deleted. Find the first failed resource under the stack's Events tab in the CloudFormation console, fix the cause, then delete the empty stack and deploy again:

PowerShell or bash
sam delete --stack-name quibble
npm run deploy
Big games feel slow, or answers in the last second are refused

Almost always the Lambda concurrency quota is still 10. Check with npm run quota:lambda, request the raise (step 6) and meanwhile deploy with npm run deploy -- LateGraceMs=5000. The dashboard's Lambda throttles graph and the quibble-lambda-throttles alarm confirm it.

"No JWT secret (aws/.jwt-secret or JWT_SECRET)" when running npm run publish

This copy of the repository has never deployed, so it has no secret to name the flag images with. If the stack already exists, copy aws/.jwt-secret from the computer that deployed it. Running npm run deploy instead creates a new secret, which logs every player out.

npm run alerts:test says "No address is subscribed" or "NOT confirmed yet"

Deploy with AlertEmail= set (step 10), then find the "AWS Notification - Subscription Confirmation" email, look in spam too, and click Confirm subscription. SNS sends nothing to an unconfirmed address.

"Missing a dependency ... Run "npm install" in the project folder"

The scripts load the AWS SDK from the project's packages. Run npm install in the quibble folder (the one with package.json), not inside aws/.

Preflight warns "live game(s) ... Deploying now can disturb them"

A deploy swaps function code and settings under running games. Wait until they finish, or end them from the admin console's Live games page, then deploy.

Part E

Ship updates

Changed some code, or pulled the latest version? Deploying again is the same command. CloudFormation compares the template with what exists and changes only the difference, so your tables and their data stay put.

PowerShell or bash
npm run deploy     # code, template or settings changed
npm run publish    # only files in public/ changed: just re-upload the website

Change a setting

Template parameters go after -- as Name=value and stay set for later deploys until you change them:

PowerShell or bash
npm run deploy -- LateGraceMs=5000 MaxPlayers=250
ParameterDefaultWhat it does
MaxPlayers250Most players one game accepts (1 to 1,000; load-tested at 250)

Try changes on a second copy first

Every script reads the stack name from QUIBBLE_STACK, so a test copy is just another name. It gets its own tables, bucket and addresses; nothing is shared with the real one.

PowerShell
$env:QUIBBLE_STACK = "quibble-test"
npm run deploy
npm run seed
# back to the real stack in this terminal:
Remove-Item Env:QUIBBLE_STACK
bash
QUIBBLE_STACK=quibble-test npm run deploy
QUIBBLE_STACK=quibble-test npm run seed

Before a big game

  • The Lambda quota is 1,000: npm run quota:lambda (request it days ahead).
  • npm run preflight passes, and no deploys are planned while a game is running.
  • The latest version is deployed; with LateGraceMs=5000 if the quota is still low.
  • You're sharing the HTTPS WebsiteUrl, or a join link from the lobby.
  • The CloudWatch dashboard is open, so you'd see throttling as it happens.

What you're learning

Updates are diffs, and environments are just stacks. Because the whole system is one template, a staging copy costs one environment variable, and a failed update rolls back to the last working version on its own (the monitor emails you when that happens). Where to go next: CloudFront in front of the bucket for a custom domain and real security headers, and Secrets Manager or SSM Parameter Store for the login secret instead of a Lambda environment variable.

Part F

Tear it all down

Done experimenting? Because everything is one stack, removing it is short. This deletes every player account, game and question for good, so export anything you want to keep from the admin console first.

1. Empty the website bucket

CloudFormation won't delete a bucket that still has files in it. This looks the bucket's name up in the stack outputs, then removes every file:

PowerShell
$bucket = aws cloudformation describe-stacks --stack-name quibble --query "Stacks[0].Outputs[?OutputKey=='FrontendBucketName'].OutputValue" --output text
aws s3 rm "s3://$bucket" --recursive
bash
bucket=$(aws cloudformation describe-stacks --stack-name quibble --query "Stacks[0].Outputs[?OutputKey=='FrontendBucketName'].OutputValue" --output text)
aws s3 rm "s3://$bucket" --recursive

2. Delete the stack

It asks you to confirm, then removes the functions, both APIs, all nine tables, the bucket, the alarms, the dashboard, the log groups, the SNS topic and the IAM roles. SAM may also offer to remove this stack's uploaded code from the SAM artifact bucket.

PowerShell or bash
sam delete --stack-name quibble

Used QUIBBLE_STACK or another region? Use that stack name in both commands, and add --region with your region code.

3. Optional clean-up

  • The SAM artifact bucket. --resolve-s3 created a separate stack, aws-sam-cli-managed-default, that every SAM project in the region shares. If you have no other SAM projects there, empty its bucket (name starting aws-sam-cli-managed-default) with the S3 console's Empty button, then delete that stack in the CloudFormation console.
  • Local files. aws/.jwt-secret and .env (it holds your admin password) can go.
  • Access. Deactivate the access key, or delete the IAM user, if you're not going to use AWS again. Keep the budget alarm.

What you're learning

A stack owns its resources. Deleting it deletes everything it created and nothing else, which is why the bucket has to be emptied by hand (its files were uploaded by a script, not created by CloudFormation) and why the SAM artifact stack survives (it belongs to SAM, not to Quibble). Check the CloudFormation console shows no quibble stack, and look at the Billing console a day later to confirm charges have stopped.
